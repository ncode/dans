# Use token-backed browser sign-in

The web console will accept an existing API token and remember sign-in across reloads and browser restarts using a secure, HttpOnly cookie with CSRF protection, for at most seven days and never beyond token expiry or revocation. This extends the header-only authentication boundary for browser use while retaining current token and authority checks; remembering sign-in must not cache permissions or delay revocation. Identity-provider integration remains deferred to minimize authentication changes in the first frontend release, and sign-out clears browser authentication without revoking the original token used by other clients.

Implementation uses opaque browser-session secrets with only their digests stored in PostgreSQL, linked to the original token. No recoverable original token or shared cookie-signing key is retained. The server enforces an absolute 168-hour lifetime and current token/identity validity. A host-scoped Secure, HttpOnly, SameSite=Strict cookie and standard-library cross-origin protection carry the session across same-version instances. Restore finalization invalidates sessions by revoking their original tokens; sign-out deletes only the current session and clears its cookie even when durable deletion cannot be confirmed.

For the requested plain-HTTP local development workflow, the root Compose stack explicitly selects `browser_cookie_mode=development-http`. Safari rejects the Secure cookie on the observed loopback HTTP origin, so this mode uses a separately named HttpOnly, SameSite=Strict cookie without Secure. Session storage, lifetime, revocation, and CSRF checks remain identical. Production defaults to the Secure cookie; requests cannot opt into development mode through Host or forwarding headers.
